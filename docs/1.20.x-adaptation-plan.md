# 1.20.x 适配计划

## 背景

- 当前稳定基线为 `1.20.1`，目标版本功能口径为 `v1.4.1`。
- 已从 `1.20.1` 切出新的集成分支：`1.20.x`。
- 本计划用于指导 `1.20.2` 到 `1.20.6` 的逐步适配、分批验证与风险收口。

## 目标

1. 以 `1.20.1` 的 `v1.4.1` 为功能基线，逐步覆盖 `1.20.2` 到 `1.20.6`。
2. 优先复用同一套业务代码，仅在必要处引入版本差异层。
3. 对每个子版本给出明确的构建结论、回归结论和是否继续共线维护的判断。

## 外部版本差异判断

### 低风险批次

- `1.20.2`
- `1.20.3`
- `1.20.4`

预期特征：

- 仍属于 Java 17 时代
- 更可能以映射、依赖、少量 API 签名变化为主
- 适合作为首轮共线验证批次

### 高风险批次

- `1.20.5`
- `1.20.6`

已确认风险：

- `1.20.5/1.20.6` 需要 Java 21
- 引入 Data Components，对 `ItemStack` 相关读写模型影响很大
- 更广泛使用 StreamCodec / 网络编解码新模型
- Fabric 侧工具链需升级到更高 Loom/Gradle 组合
- Forge 侧进入 `50.x` 代际，不再适合沿用 `47.2.0`

## 关键结论

`1.20.x` 分支应被视为“1.20 系列集成分支”，而不是默认保证 `1.20.1` 到 `1.20.6` 永久完全同构的单源码分支。

推荐治理策略：

1. `1.20.2` 到 `1.20.4` 先尝试共线维护。
2. `1.20.5` 到 `1.20.6` 作为高风险簇单独验证。
3. 如高风险簇导致构建脚本、JDK、网络层或物品数据层出现持续分叉，则在 `1.20.x` 内引入版本差异层；若差异层过重，再考虑拆出 `1.20.5+` 分支。

## 分阶段执行方案

### Phase 0：执行前提收口

目标：

- 在进入任何试编、构建或测试动作前，先补齐 `1.20.x` 分支的合规执行规则。

工作项：

1. 明确 `1.20.x` 分支不再仅按 Git 分支名选择构建脚本，而是按“目标 Minecraft 子版本”选择 JDK 与构建入口。
2. 形成最小规则：
   - `1.20.1` 到 `1.20.4` 默认使用 Java 17
   - `1.20.5` 到 `1.20.6` 默认使用 Java 21
3. 明确后续执行口径采用以下二选一方案：
   - 补充新的统一构建入口脚本，由脚本接收目标子版本并选择 JDK
   - 更新项目规则，允许 `1.20.x` 分支按目标子版本切换 `build-local-17.bat` / `build-local-21.bat`
4. 在计划正文或配套规则中写明，Phase 1 之后的任何“构建通过”“试编通过”“测试通过”结论，都必须附带目标子版本与 JDK 选择依据。

完成标准：

- `1.20.x` 分支已有明确、可复用、可审计的构建脚本/JDK 选择规则。
- 后续 Phase 1 到 Phase 4 的构建验证具备合规执行路径。

### Phase 1：参数化与基线清理

目标：

- 把当前仅适用于 `1.20.1` 的版本硬编码抽离为可切换配置。

工作项：

1. 建立 `1.20.x` 的单一事实来源版本矩阵，至少覆盖：
   - Minecraft 子版本
   - JDK
   - Gradle Wrapper
   - Loom
   - mappings
   - Fabric Loader
   - Fabric API
   - Forge
2. 为 Fabric、Forge、元数据文件建立统一的版本参数入口，并全部从上述矩阵派生。
3. 为 Forge 版本号单独增加配置项，避免与 `minecraft_version` 绑定死。
4. 评估 `fabric.mod.json` 与 `mods.toml` 是否改为资源展开或模板替换。
5. 清理源码中会误导后续移植的 `1.20.1` 专属注释。

完成标准：

- 已存在一份可复用的版本矩阵，后续各子版本切换均从同一输入源派生。
- 同一套构建流程可在不改源码的前提下切换到目标子版本配置。
- `1.20.1` 基线重新构建通过。

### Phase 2：1.20.2 试点适配

目标：

- 用最小成本验证 `1.20.x` 共线策略是否成立。

工作项：

1. 建立 `1.20.2` 的版本参数组合。
2. 先修复构建失败，再修复编译失败，再修复运行期入口失败。
3. 记录所有差异点，分类为：
   - 配置差异
   - 映射差异
   - API 差异
   - Loader 差异
   - 行为差异

完成标准：

- Fabric、Forge 均能完成构建。
- 不引入破坏 `1.20.1` 的回归。
- 形成首版差异清单。

### Phase 3：扩展到 1.20.3 和 1.20.4

目标：

- 验证 `1.20.2` 的适配方式是否可复用到中段子版本。

工作项：

1. 复用 `1.20.2` 的参数化方案继续推进。
2. 对新增差异点做“是否通用化”的判断。
3. 若某差异只影响单版本，优先收敛到小范围兼容分支或工具类。

完成标准：

- `1.20.2` 到 `1.20.4` 形成稳定共线结论，或明确出现第一处分叉边界。

当前结论：

- `1.20.3` 与 `1.20.4` 均已完成完整 `build` 验证。
- `NBT` 文件读写签名差异与 GUI 列表 API 分叉已经收口为通用兼容层，可继续维持 `1.20.1` 到 `1.20.4` 共线。
- 下一阶段可将重心转向 `1.20.5` 与 `1.20.6` 的 Java 21 和更高版本 API 风险。

### Phase 4：单独评估 1.20.5 和 1.20.6

目标：

- 判断高风险批次是否还能纳入同一维护轨道。

工作项：

1. 建立 Java 21 构建入口。
2. 升级 Loom、Fabric Loader、Fabric API、Forge 版本矩阵。
3. 检查项目是否直接依赖以下旧模型：
   - `ItemStack` 的 NBT 读写
   - 旧网络包编解码方式
   - 与 Data Components 冲突的物品数据读写习惯
4. 审核是否需要对平台层做版本分流。

完成标准：

- 明确回答以下问题：
  - `1.20.5/1.20.6` 能否与 `1.20.1~1.20.4` 共线？
  - 若能，共线成本是否可接受？
  - 若不能，最小拆分边界在哪里？

当前结论（2026-08-16）：

- `1.20.6` 可以与 `1.20.1~1.20.4` 共线，全量构建与运行时测试已验证。
- 共线成本集中在三处平台兼容层，均为一次性投入：
  1. Fabric 网络层：`FabricNetworkingCompat`（反射 + 动态代理桥接 payload API）。
  2. Forge HUD 事件层：`ForgeTodoClient` 反射注册 `RenderGuiOverlayEvent/RenderGuiEvent`。
  3. 测试基建：`needs1205TestShim` 生成阶段注入服务器抽象方法与静态实例。
- 业务层（项目/任务协议、存储、GUI 逻辑）未做版本分流，`ResourceLocation + FriendlyByteBuf` 协议保持不变。
- 剩余注意事项：
  - `FabricNetworkingCompat` 的新 payload 分支依赖运行时反射，首次发包路径建议在真实联机环境冒烟验证。
  - `1.20.5` 已定位为 Fabric-only：官方无 Forge 发布链，构建链通过 `forge_supported=false` 跳过 Forge 侧产物。
  - Data Components 对 `ItemStack` 的影响未触发，本 mod 未直接操作物品 NBT。
- `1.20.5` 与 `1.20.6` 的最终答案：
  - 两者均与 `1.20.1~1.20.4` 共线；`1.20.6` 为 Fabric + Forge，`1.20.5` 为 Fabric-only。

### Phase 5：矩阵入库与发布治理

目标：

- 把可维护结论沉淀为固定流程，不再每次重新摸索。

当前进展（2026-08-16）：

- `gradle/version-matrix.properties` 已成为全版本单一事实来源：
  - 记录 `1.20.1~1.20.6` 的 Minecraft/Java/Gradle/Loom/Fabric Loader/Fabric API/Forge/依赖区间与 `forge_supported` 开关。
  - 状态键已回写：`1.20.1` stable-baseline；`1.20.2~1.20.4` trial/matrix-filled；`1.20.5` fabric-only-build-verified；`1.20.6` build-verified-with-1201-1204-regression。
- `ROADMAP.md` 支持矩阵已更新：`1.20.x` 标注 `1.20.5` 仅 Fabric，并补记本轮执行记录。
- 统一构建入口保持唯一：`.\build-local-120x.bat <mc版本> build [--offline]`。

待办：

- 各版本产物打包命名与 changelog 约定（发布治理）。
- 真实联机冒烟：`FabricNetworkingCompat` payload 反射分支的收发验证。

工作项：

1. 将 Phase 1 已落地的版本矩阵沉淀为正式文档与长期维护入口。
2. 为每个子版本记录：
   - Java 版本
   - Gradle 版本
   - Loom 版本
   - mappings 方案
   - Loader 版本
   - Fabric 版本组合
   - Forge 版本组合
   - 是否共线
   - 已知限制
3. 更新 `ROADMAP.md` 与后续发布说明。

## 验证口径

每个子版本至少覆盖以下检查：

1. 构建验证
   - Fabric 构建通过
   - Forge 构建通过
2. 启动验证
   - 模组正常加载
   - 核心命令可注册
3. 功能验证
   - 个人任务增删改查
   - 团队任务与权限操作
   - 子任务创建、排序、完成、显示
   - HUD 显示与刷新
4. 存储验证
   - H2 初始化
   - H2 读写
   - 已有数据迁移链路不回退
5. 回归验证
   - 不破坏 `1.20.1` 当前功能闭环

## 当前推荐推进顺序

1. 先完成 Phase 0 的执行前提收口。
2. 再完成 Phase 1 的矩阵化与参数化改造。
3. 然后只选 `1.20.2` 做第一轮试编。
4. `1.20.2` 成功后再推进 `1.20.3/1.20.4`。
5. 最后单独进入 `1.20.5/1.20.6` 高风险评估。

## 当前阻塞与注意事项

### 已解决的前置阻塞

- `1.20.x` 分支内的 JDK 选择冲突已通过 `build-local-120x.bat` 收口，当前可以按目标 Minecraft 子版本稳定切换 Java 17 / Java 21。
- `1.20.3+` 暴露出的 Forge 依赖解析、`NbtIo` 签名差异、GUI 列表 API 分叉已经完成首轮收口。

### 下一阶段主要风险

- `1.20.5` 与 `1.20.6` 需要切到 Java 21，构建链与运行期 API 变更都明显高于 `1.20.2` 到 `1.20.4`。
- `1.20.5+` 若出现大面积 UI、网络、数据组件差异，需要重新评估是否继续维持单轨共线。

### 不建议现在就做的事

- 不建议一开始就同时改 `1.20.2` 到 `1.20.6`
- 不建议在未完成参数化前直接大面积改源码
- 不建议在 `1.20.5/1.20.6` 尚未验证前承诺整个 `1.20.x` 永久单轨
