# H2 存储迁移 M3 详细计划：备份、维护锁与 reload-db

## 关联总计划

- 总计划：[h2-storage-migration-plan.md](h2-storage-migration-plan.md)
- 本阶段增加备份、维护锁、`reload-db` 和 schema 升级前备份。

## 通用执行门禁

- 每个阶段开始前先确认上一个阶段的验收项已通过；未通过时不得继续叠加下一阶段功能。
- 每个阶段只实现本阶段明确列出的能力；发现需要跨阶段能力时，先更新总计划和本阶段文档并说明原因，再实施。
- 每个阶段都必须保持 `storageBackend=nbt` 可用，且 NBT 模式不得加载、初始化或写入 H2。
- 每个阶段都必须保持现有命令、GUI、HUD、网络同步行为不因未开启 H2 而变化。
- 每个阶段的 Java 新增类和新增方法都必须按项目规则补充简短说明注释。
- 每个阶段完成后执行对应阶段测试；涉及代码实现阶段还要执行 `.\build-with-java21.bat --offline build`。
- 发现中文乱码、旧 `.dat` 被意外修改、H2-only 数据被旧 NBT 覆盖、或 H2 失败后内存出现未保存脏状态时，立即停止本阶段并先修复问题。

## 阶段内审查循环

- 实施前按“执行前检查清单”和“禁止事项”审查。
- 每完成一个实施步骤，按“验收标准”和“最小测试矩阵”复审。
- 发现计划缺口时，先改进总计划和本阶段文档，再继续实施。
- 重复审查和改进，直到没有新的计划改进建议。

## 目标

- 增加面向运维的备份、维护锁、schema 升级前备份和 `reload-db`。
- 保证维护期间玩家修改不会被覆盖或伪保存。

## 阶段输入

- M1 的 H2 状态模型、Storage 门面、写入口和不可用异常。
- M2 的连接模式状态，包含 TCP 与嵌入式回退路径。
- 当前所有保存触发点：用户操作、命令、网络同步、后台定时保存、退出保存。
- H2 目标版本已验证的 `BACKUP TO` 或等价备份能力。

## 执行前检查清单

- 确认 M1 的所有写入口清单仍然最新。
- 确认 M2 的 TCP/嵌入式连接状态能被运维命令读取。
- 确认 H2 backup 方案已在目标版本上验证，不依赖未确认 API。
- 确认 schema upgrade 失败时的默认策略是存储不可用，不自动展示过期旧 `.dat`。

## 阶段产出

- 全局维护锁组件和所有写入口接入。
- `/todolist h2 backup [name]`、`/todolist reload-db` 和健康检查能力。
- schema upgrade 框架、升级前自动备份和升级失败状态。
- 维护期间 GUI/命令/网络写入拒绝提示。
- backup、reload、schema upgrade 组合测试。

## 实施步骤

1. 新增全局维护锁组件，提供读状态、进入维护、退出维护、拒绝写入和用户提示原因。
2. 将任务、项目、玩家项目状态、后台定时保存、退出保存、网络同步保存统一接入维护锁检查。
3. 维护锁占用时，写入口在修改内存前失败，不得先改对象再保存。
4. 实现 `/todolist h2 backup [name]`，仅控制台或 OP 可执行，输出预计影响和最终备份路径。
5. backup 执行期间暂停写入，并使用 H2 `BACKUP TO` 或已验证的等价方式生成一致性备份。
6. 新增 `backupOnStart` 配置，默认 false；schema version 小于当前代码版本时升级前强制备份。
7. 新增 schema upgrade 框架：版本读取、升级步骤、事务边界、失败状态和升级后版本写入。
8. schema 升级失败时不更新 `schema_version`，不允许半升级库继续写入。
9. 实现 `/todolist reload-db`：后台线程读取当前配置后端，成功后主线程切换内存状态并刷新 GUI/HUD。
10. reload 失败时保留旧内存状态，释放维护锁并提示错误。
11. 新增健康检查：`SELECT 1`、读取 `storage_meta`、`SELECT COUNT(*) FROM tasks`。

## 禁止事项

- 不允许任何保存路径绕过维护锁。
- 不在 `storageBackend=h2` 的 `reload-db` 中读取旧 `.dat`。
- 不在 `storageBackend=nbt` 的 `reload-db` 中触发 H2 初始化。
- 不在 schema 升级失败后自动展示过期旧 `.dat`，除非符合 M1 fallback 条件或用户显式选择恢复。
- 不实现 M4 的 GUI/HUD SQL 查询优化。
- 不允许 backup、reload 或 schema upgrade 与普通保存并发修改同一份内存状态。

## 停止条件

- 无法枚举并接入所有保存触发点。
- 维护锁只能拦截数据库写入，但不能阻止内存对象先被修改。
- backup 期间仍会发生后台保存、退出保存或网络同步保存。
- schema 升级失败后仍会继续写入半升级库。
- reload 失败会丢弃旧内存状态或刷新 GUI/HUD 为失败结果。

## 验收标准

- backup 期间所有写入口都被拒绝并给出“数据库维护中”类提示。
- backup 文件可被验证为包含当前 H2 数据，且备份过程中不产生内存脏状态。
- schema 升级前自动备份；升级失败不更新版本、不继续写入半升级库。
- 已完成迁移并产生 H2-only 数据后，schema 升级失败不会自动展示旧 `.dat`。
- reload 成功时 GUI/HUD 刷新为新状态；reload 失败时旧内存状态不变。
- 健康检查能区分正常、不可用、fallback 和空状态。
- `.\build-with-java21.bat --offline build` 和 M1/M2 回归测试仍通过。

## 可进入下一阶段条件

- 维护锁已覆盖所有写入口，并通过保存、退出、网络同步、backup、schema upgrade、reload 的组合测试。
- 运维命令失败时不会造成数据覆盖、半升级或脏内存。

## 最小测试矩阵

- 维护锁覆盖：GUI 保存、命令保存、网络同步保存、后台定时保存、退出保存。
- backup：正常备份、命名备份、备份期间写入拒绝、备份失败释放维护锁。
- schema upgrade：无需升级、升级成功、升级失败、升级前备份失败、已迁移库失败不得旧数据 fallback。
- reload：H2 reload 成功、H2 reload 失败、NBT reload 不触发 H2、reload 期间写入拒绝。
- 健康检查：正常、storage_meta 缺失、tasks 查询失败、H2 文件锁、fallback 状态。
- M2 组合：TCP 模式下 backup/reload，TCP 失败回退嵌入式后的 backup/reload。

## 回滚方式

- 禁用新增运维命令入口，保留 M1/M2 正常读写路径。
- schema 升级失败时使用升级前备份作为人工恢复依据，不自动覆盖当前库。
- reload 失败时保留旧内存状态和旧连接状态，不切换 GUI/HUD。

## 文档同步要求

- 新增写入口、维护锁状态或运维命令时，同步更新 M1 写入口清单和总计划 M3 小节。
- schema version、升级步骤或升级失败策略变化时，同步更新总计划 Schema 和旧数据回退说明。
- backup 文件命名、路径或恢复流程变化时，同步更新本阶段验收和回滚方式。
