# H2 存储迁移 M4 详细计划：SQL 查询优化

## 关联总计划

- 总计划：[h2-storage-migration-plan.md](h2-storage-migration-plan.md)
- 本阶段将 GUI/HUD 高频全量扫描逐步改为 SQL 查询。

## 通用执行门禁

- 每个阶段开始前先确认上一个阶段的验收项已通过；未通过时不得继续叠加下一阶段功能。
- 每个阶段只实现本阶段明确列出的能力；发现需要跨阶段能力时，先更新总计划和本阶段文档并说明原因，再实施。
- 每个阶段都必须保持 `storageBackend=nbt` 可用，且 NBT 模式不得加载、初始化或写入 H2。
- 每个阶段都必须保持现有命令、GUI、HUD、网络同步行为不因未开启 H2 而变化。
- 每个阶段的 Java 新增类和新增方法都必须按项目规则补充简短说明注释。
- 每个阶段完成后执行对应阶段测试；涉及代码实现阶段还要执行 `.\build-with-java21.bat --offline build`。
- 发现中文乱码、旧 `.dat` 被意外修改、H2-only 数据被旧 NBT 覆盖、或 H2 失败后内存出现未保存脏状态时，立即停止本阶段并先修复问题。

## 阶段内审查循环

- 实施前按“执行前检查清单”和“禁止事项”审查。
- 每完成一个查询替换点，按“验收标准”和“最小测试矩阵”复审。
- 发现计划缺口时，先改进总计划和本阶段文档，再继续实施。
- 重复审查和改进，直到没有新的计划改进建议。

## 目标

- 在 M1-M3 稳定后，逐步把 GUI/HUD 高频全量扫描替换为 SQL 查询。
- 保持现有展示语义和排序稳定，同时降低大数据量下的加载和刷新成本。

## 阶段输入

- M1-M3 已稳定的 H2 DAO、reload、维护锁和缓存刷新机制。
- 当前 GUI/HUD 的内存过滤逻辑、排序规则、空值处理和权限边界。
- 当前 NBT 模式下的内存数据模型。
- 大数据量样本或可生成测试数据的工具。

## 执行前检查清单

- 确认 M1-M3 的迁移、TCP、backup、reload 和维护锁测试全部通过。
- 确认每个待替换 UI 入口都有原内存过滤结果作为对照基准。
- 确认 DAO 查询层已有参数绑定工具或明确的 PreparedStatement 规范。
- 确认 NBT 模式保留等价路径，不因 SQL 化而退化。

## 阶段产出

- GUI/HUD 全量扫描入口清单和替换优先级。
- DAO 查询方法和查询服务封装。
- SQL 与原内存过滤结果一致性的对照测试。
- 项目侧栏计数、HUD 列表、GUI 筛选/搜索的逐步 SQL 化。
- 缓存失效和刷新策略说明。

## 实施步骤

1. 盘点 GUI/HUD 当前全量扫描入口，记录调用方、过滤条件、排序规则和刷新时机。
2. 在 DAO 层补齐查询方法：项目计数、HUD 任务列表、星标项目、搜索、优先级、完成状态、负责人、项目过滤。
3. 每个 SQL 查询先建立与现有内存过滤结果一致的对照测试，再替换调用方。
4. 项目侧栏计数优先改为 `GROUP BY project_id`，保持未分配项目和跨桶边界语义。
5. HUD 查询按视图、范围、星标项目、显示数量和完成状态使用 SQL limit，避免全量加载。
6. GUI 搜索和筛选逐步改 DAO 查询；复杂组合筛选必须保持现有排序和空值处理。
7. 大列表引入分页或 limit 时，明确滚动、选中项、编辑后刷新和删除后的定位行为。
8. 保留必要的内存缓存，但缓存必须可通过 `reload-db` 和保存成功事件失效或刷新。
9. 对每个替换点增加回归测试，验证 SQL 结果与原内存过滤结果一致。

## 禁止事项

- 不在 M4 中改变 schema v1，除非先作为 schema v2 进入 M3 升级流程。
- 不为了查询优化绕过权限判断、项目成员过滤或桶边界。
- 不让 GUI/HUD 直接拼接 SQL；SQL 只能由 DAO 或查询服务封装。
- 不牺牲 NBT 模式；`storageBackend=nbt` 仍使用原有内存模型或等价查询适配。
- 不在查询优化中改变用户可见排序、筛选语义或权限语义。

## 停止条件

- 无法为某个 SQL 查询建立与原内存过滤一致的对照测试。
- SQL 查询需要 GUI/HUD 直接拼接用户输入。
- NBT 模式没有等价路径，导致后端切换后 UI 行为分叉。
- reload-db、保存成功或 namespace 切换后查询缓存无法可靠失效。
- 性能优化会改变用户可见排序或遗漏权限过滤。

## 验收标准

- 项目侧栏计数、HUD 列表、GUI 搜索/筛选与原内存过滤结果一致。
- 大数据量下 HUD 和 GUI 刷新不再依赖全量扫描关键路径。
- SQL 查询都有参数绑定，不拼接用户输入。
- 保存、删除、reload-db、namespace 切换后查询结果及时刷新。
- `.\build-with-java21.bat --offline build` 和全部回归测试通过。

## 最终完成条件

- NBT 与 H2 两种后端均可运行，默认后端策略已明确。
- H2 嵌入式、TCP、备份、reload、schema 升级和 SQL 查询优化均有测试覆盖。
- 文档中的禁止事项和 fallback 边界均已由测试或实现约束覆盖。

## 最小测试矩阵

- 项目计数：个人项目、团队项目、未分配任务、已完成/未完成过滤、跨桶同 ID。
- HUD：个人/团队视图、星标项目、数量 limit、空列表、完成状态切换。
- GUI 搜索：中文关键字、大小写、标题/描述/标签、负责人、优先级、项目过滤组合。
- 排序：`sort_order`、`created_at`、`id` 稳定排序和分页边界。
- 缓存：保存成功、删除、reload-db、namespace 切换、TCP 重启后查询刷新。
- 安全：所有用户输入走参数绑定，权限过滤不能被搜索条件绕过。
- NBT 兼容：`storageBackend=nbt` 下仍使用原内存模型并保持同样展示结果。

## 回滚方式

- 单个查询替换失败时，回退该入口到原内存过滤实现。
- 保留 DAO 查询方法但不接入 GUI/HUD，直到对照测试补齐。
- 若缓存失效不可靠，优先关闭缓存或回退到 M3 的全量内存刷新模型。

## 文档同步要求

- 新增查询索引、schema v2 或查询语义变化时，同步更新总计划 Schema/M4 小节和 M3 schema upgrade 说明。
- GUI/HUD 展示语义、排序或分页行为变化时，同步更新本阶段测试矩阵。
- 若某个入口决定暂不 SQL 化，在总计划 M4 小节标明保留原因和后续条件。
