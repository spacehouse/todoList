# 需求评审模板

> 用途：任何新需求（包括自己的想法）进入 `TODO.md` 计划中之前，先用本模板回答「需求准入三问」。
> 立项动机：本项目曾在缺少评审的情况下投入实机验证成本后被证伪回退（Phase Z，见 `docs/feat-trigger-credit-allocation.md` §0），
> 也曾凭空设想社区并不存在的需求（材料反推点 2 / 点 3，见 `docs/feat-material-task-generation.md` §0）——模板就是为了把这两类代价拦在动手之前。
>
> 填写原则：一页写完，写不清楚就是没想清楚；每项必答，答不出来的需求不进计划。

## 模板正文（复制使用）

```markdown
## <需求名>（<日期>）

### 1. 用户故事（准入问题一：谁在什么场景需要它）

- 作为 <谁>，我想 <做什么>，以便 <得到什么>。
- 场景描述：<玩家实际操作路径，一段话>
- 需求来源（勾选并附证据）：
  - [ ] 社区反馈（Issue / 群聊 / 评论，附链接或截图）
  - [ ] 自己遇到的真实痛点（描述当时情境）
  - [ ] 自己的设想（**此项需额外谨慎**：无任何外部佐证时，默认按 experimental 立项并设置更短的投入上限）

### 2. 验证方案（准入问题二：实机怎么验、验收标准是什么）

- 验收标准（可勾选的清单，做完即算通过）：
  - [ ] <标准 1>
  - [ ] <标准 2>
- 实机验证路径：在 <版本/加载器> 中执行 <操作序列>，预期 <结果>。
- 离线可覆盖部分：哪些断言可以进 `:common:check` / 自动化验证，不必占用实机时间。

### 3. 投入上限（准入问题三：超了就冻结）

- 生产代码预估：<行数 / 文件数>
- 时间 / token 预算：<上限值>
- 触发冻结的条件：<写明什么信号出现时立即停手，如"首个实机轮次证伪核心语义""预估超限 50%">

### 4. 状态流转

- 当前状态：计划（→ experimental → stable）
- experimental 转正条件：<拿到什么社区反馈后转正；长期无反馈的到期处理（冻结/移除日期）>
- 归档：实现后回填 TODO.md 条目位置与设计文档链接。
```

## 使用约定

1. **评审通过的标准**：三问全部答完、验收标准可勾选、冻结条件具体可判定——满足才允许把条目写进 `TODO.md` 计划中。
2. **归档位置**：评审通过后，本文档内容并入该需求的设计文档（`docs/feat-*.md`）头部，模板文件本身不留存条目。
3. **experimental 的含义**：对外发布但明示实验性；只修缺陷不扩能力；无社区反馈不转正（详见 `TODO.md` 维护约定）。
4. **附属 / 外部集成类需求**（独立模组承载，见 `TODO.md` 计划中相应小节）：同样过三问，但"投入上限"按附属项目独立核算。

## 反例存档（供对照，不要重复）

- **Phase Z（额度配额）**：三问中"验证方案"若在动手前认真回答（新建同物品任务→消耗物品→再建任务，观察进度），
  台账机制在纸面推演阶段即可被证伪——实际却在实现并实机验证后才回退。
- **材料反推点 2 / 点 3**：用户故事里"谁需要模组配方反推"始终只有设想输入，没有社区反馈来源；
  冻结评审（2026-10-25）确认其为典型自造需求，交由 JEI/EMI 附属承接。
