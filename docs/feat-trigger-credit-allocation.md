# 同物品任务的额度配额（Phase Z 设计稿）

> 状态：**已定方案，尚未实现**（用户 2026-09-15 确认：方案 1 全量额度配额 + 合成走 1a 轻量实现）
> 关联：`docs/feat-trigger-completion.md`（触发器语义底座）、`docs/feat-material-task-generation.md`（材料反推生成的收集/合成任务链）

## 1. 问题

同一个项目里，如果多条任务（含子任务）追踪**同一种物品**，拿到一份物品会把它们**同时**判为完成：

| 触发类型 | 现有判定 | 现象 |
|---|---|---|
| `ITEM_COLLECT` 收集 | 进度 = 当前背包持有量（绝对量），每条任务各自与同一份背包比较 | 拿到 16 个铁锭 → 所有目标 ≤16 的收集任务一起达标 |
| `CRAFT_ITEM` 合成 | 一次合成事件累加给**所有**同物品未完成任务 | 合成 4 个木板 → 两条"需要 4 个"的任务一起完成 |

根因：引擎里任务之间没有任何额度协调，见 `TaskTriggerService.advanceMatchingTasksByUuid`
与 `recalculateItemCollectByUuid`，两者都是**逐任务独立判定**。物品既没有被真正消耗，
任务之间也不记账，因此同一份物品可以"重复满足"任意多条任务。

这在材料反推场景下很常见：一个项目里几个不同的合成目标，各自都需要木板，
就会生成多条"收集 橡木木板 ×N"，全部被同一批木板同时完成。

## 2. 设计目标与硬约束

1. **不共享**：同一份物品只能满足它实际够用的那部分需求；
2. **已完成不回退**：项目既有规则（`docs/feat-trigger-completion.md`），任何改动都不能破坏；
3. **零新增持久化**：不新增表/字段，重启、重进世界、多人同步后结果必须一致；
4. **单条任务行为不变**：某物品只有一条任务时，语义与现在完全一致（避免大范围回归）；
5. **可离线测试**：判定逻辑不依赖 MC 运行时对象。

## 3. 方案：额度配额（方案 1）

### 3.1 核心思路

把「同一分组」下的任务看作对同一份资源的**多次申领**，判定前先扣掉已被其它任务占用的部分。
**台账就是"已完成任务"本身**，不需要新表：

```
已占用 used = Σ(同组内【已完成】任务的 targetCount)
```

分组键 = `(所属桶/项目, 触发器类型, 目标物品, 负责人 UUID)`

- 个人任务：负责人即玩家自己；
- 团队任务：按 `assigneeUuid` 分组，未指派（待领取）的任务不参与（既有规则）；
- 不同项目 / 不同作用域天然隔离。

### 3.2 收集类（ITEM_COLLECT）算法

```
held = 该玩家对该物品的当前持有量（沿用现有 countHeldItems 口径）
used = Σ(同组已完成任务的 targetCount)

未完成任务按 (createdAt 升序, id 兜底) 贪心：
    available = max(0, held - used)
    progress  = min(available, targetCount)      // 展示用
    if (available >= targetCount) {
        标记完成（占用额度）
        used += targetCount                       // 一轮内即时累加
    }
```

关键点：**未完成的任务不占用额度**，所以"需求更小的那条会先被满足"。

### 3.3 合成类（CRAFT_ITEM）算法 —— 1a 轻量实现

合成是"任务创建后新合成"的相对量，各任务累加的是同一事件流的副本，但**创建时间不同的任务看到的量不同**，
因此不能直接套用"持有量 − 已占用"。1a 的做法是：

```
raw = 该任务自身累加量（trigger.getProgress()，语义不变）
used = Σ(同组已完成任务的 targetCount)

未完成任务按 (createdAt 升序, id 兜底)：
    available = max(0, raw - used)
    if (available >= targetCount) { 完成; used += targetCount; }
```

语义边界（已知偏差，见 §7）：

- 对**同一时刻批量创建**的任务（材料反推生成的子任务链、批量新建）完全正确；
- 对先后手工创建的任务，因为各任务累加起点不同，结果偏向"先创建的先被满足"；
- 若要完全严谨，需要 1b：新增"每玩家每物品累计合成量"并持久化 + 任务记录创建基线，
  属于动表结构的改造，本阶段不做。

### 3.4 行为示例

两条任务：`收集 铁锭 ×32`（先建）、`收集 铁锭 ×16`（后建）：

| 背包持有 | 铁锭 ×32 | 铁锭 ×16 | 说明 |
|---|---|---|---|
| 0 | 0/32 未完成 | 0/16 未完成 | 都没占用 |
| 16 | 16/32 未完成 | **16/16 完成** | 小的先满足并占掉 16 |
| 16（上一行之后） | 0/32 未完成 | 已完成 | 32 那条要**重新**攒 32 个 |
| 48 | 32/32 完成 | 已完成 | 合计 48，不再共享 |

两条 `合成 木板 ×4`（同批创建）：

| 累计合成 | 任务 A | 任务 B | 说明 |
|---|---|---|---|
| 4 | **4/4 完成** | 0/4 未完成 | 一次事件不再同时满足两条 |
| 8 | 已完成 | **4/4 完成** | 合计 8 才全部完成 |

## 4. 边界与一致性命中检查

| 场景 | 期望行为 | 是否满足硬约束 |
|---|---|---|
| 已完成后玩家丢弃物品，持有量下降 | 已完成任务保持完成；未完成任务的展示进度可下降 | ✅ 只影响未完成任务显示 |
| 取消勾选 / 删除某条已完成任务 | 释放它的额度；后面的任务可能因此"提前完成" | ✅ 只会更早完成，不回退 |
| 修改同物品某任务的 targetCount | 该组额度重算；已完成的保持完成 | ✅ |
| 团队任务改派 / 取消领取 | 换人后按新负责人的组重新分配；旧组额度释放 | ✅ 与既有"进度清零"规则一致 |
| 未指派的团队任务 | 不参与分组与判定 | ✅ 既有规则 |
| 某物品只有一条任务 | `used = 0`，`available = held(raw)`，行为与现在完全一致 | ✅ |
| 手动勾选完成 | 既然是手动，直接计入"已完成"→ 自动占用额度 | ✅ 与"触发器优先 + 可手动勾选"一致 |
| 父任务带触发器（触发器优先） | 父任务不因聚合完成；额度分配同样只看它自己的完成态 | ✅ 不侵入既有规则 |
| 同一轮内多条同时达标 | 贪心逐个占用，额度不会重复分配 | ✅ |

排序稳定性：`createdAt` 为主键、`id` 兜底。**不要用显示顺序**——显示顺序可被拖拽改变，
按它分配会让阈值来回变动。`createdAt` 不可变，天然满足"不回退"。

## 5. 实现要点

### 5.1 新增纯逻辑组件

`com.todolist.trigger.TriggerCreditAllocator`（无 MC 依赖，可离线单测）：

```
输入：候选任务（同组、未完成） + 每条任务的"原始可用量" + 已完成的同组任务
输出：{ 任务 → 展示进度, 应完成任务集合 }
```

### 5.2 接入点

| 位置 | 现状 | 改法 |
|---|---|---|
| `TaskTriggerService.recalculateItemCollectByUuid` | 逐任务 `setProgress(held)` + `isSatisfied()` | 改为"收集原始量 → 交给分配器 → 回写展示进度 + 完成集合" |
| `TaskTriggerService.advanceMatchingTasksByUuid` | 循环内 `addProgress(amount)` 后立即判完成 | 改为两阶段：先对全部匹配任务累加（不判定），再统一交给分配器判定完成 |
| `completeTask` / `bucket.markDirty` / `removeIndex` / 通知推送 | 既有链路 | 完成动作仍走原链路，不改 |

注意：`advanceMatchingTasksByUuid` 的候选列表副本遍历（防 `ConcurrentModificationException`）
两阶段改造后依然要保留；`removeIndex` 必须在判定完成后统一执行。

### 5.3 显示与文案（待定 UI 决策）

收集类任务的右侧进度会从"持有量/需求"变成"**可用份额/需求**"。
上面的例子里，`铁锭 ×32` 会在另一条完成后显示 `0/32`——判定正确，但玩家可能疑惑。

两个候选处理：

- **A**：任务右侧进度旁加后缀提示（如 `0/32（同物品已占用 16）`）或 tooltip；
- **B**：不改文案，靠 `/todo h2` 之类文档说明"同物品任务共享额度"。

实现时二选一，倾向前者，但文案需要先定，避免后面反复改。

## 6. 测试计划

离线（扩展 `TaskTriggerServiceTestMain`，纯逻辑入口现成）：

1. 两条同物品收集任务：持有只够小的 → 只完成小的，大的显示 0/N；
2. 持有够全部 → 两条都完成；
3. 持有回落到不足 → 已完成不回退；
4. 删除 / 取消完成一条 → 额度释放，另一条可完成；
5. 两条同批合成的任务：合成量只够一条 → 只完成一条，再合成够第二条 → 完成；
6. 单条任务行为与既有用例一致（全部旧用例保持绿）；
7. 团队：不同负责人各算各的；未指派不参与；
8. 幂等：同一快照重复执行结果一致（为防抖/重算路径准备）。

实机清单（追加到 `feat-trigger-completion.md` §8）：在一个项目里建两条同物品收集任务，
捡够其中较小的需求量，确认只有一条完成；再补齐差额，确认第二条完成。

## 7. 风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 进度语义变化不易理解 | 同物品任务的进度不再是"背包持有量" | §5.3 文案；文档说明 |
| 合成类 1a 的先后创建偏差 | 先后手工建的任务偏向"先建先满足" | 明确写入 §3.3；需要严谨时再做 1b |
| 排序依赖 `createdAt` | 同毫秒创建需要 `id` 兜底才稳定 | 兜底 + 幂等测试 |
| 老存档首次升级的行为跳变 | 已完成的同物品任务会立即占用额度，未完成任务进度可能下降 | 只影响未完成任务显示，不回退已完成；实机验证一次 |
